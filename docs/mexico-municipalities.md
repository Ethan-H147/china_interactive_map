# Mexico municipalities and boroughs

Mexico has two map levels: **States & Mexico City** and **Municipalities & boroughs**. The second level contains every municipal key in INEGI's December 2025 vector service: 2,462 municipalities and the 16 Mexico City boroughs (alcaldías), for 2,478 units. All 32 federal entities have a geometry chunk, including Oaxaca's 570 municipalities and Baja California's seven.

The boundary and tabular responses for each federal entity are retained under `scripts/boundary-sources/mexico-municipalities/`. Their key lists must match exactly. The manifest records retrieval date, source URLs, metadata and SHA-256 hashes. These are INEGI statistical reference areas, with their stated December 2025 boundary date, rather than a claim to a newer boundary release.

Municipal polygons are cleaned and simplified together at .0001 degrees, about 11 metres north-south. State shapes are dissolved from the same arcs. Validation requires the exterior segment set of every state's municipalities to match its state polygon exactly. Shared municipal boundaries are drawn once; shorelines receive a stroke only when selected. Existing international-border references and optional water layers remain in use.

Geometry loads one federal entity at a time. The national search catalogue contains names, official five-digit keys, parent names and municipal-seat aliases. Seat names missing from the vector responses are extracted from the retained 2020 census ITER archive using each municipality's official seat code. For example, Cancún remains a seat alias for Benito Juárez municipality in Quintana Roo. The independent locality layer now puts Cancún’s city result first; the municipality remains a separate result. City names do not create extra municipal units.

The 2020 census population is available for 2,469 units. Nine newer municipalities have no population in this service: their figures remain unavailable. Local areas are calculated from their mapped geometry. Municipalities do not inherit state GDP. State population and economic data are preserved. Population and density shading includes the municipal level where figures exist.

Rebuild with `npm run build:mexico-municipalities`. The ordinary country-expansion builder also calls this build for Mexico. Run `npm run test:mexico-municipalities` and `npm run test:mexico-municipalities-browser`; existing Mexico water checks cover the separate hydrography overlay. Browser checks cover desktop and phone searches, saved selection, all 16 boroughs, a small Oaxaca municipality, an unavailable census value, municipal-seat aliases and cleanup on country switching.

## Cities, towns and villages

Mexico also has 189,432 independent locality points from INEGI’s national 2020 ITER census extract. Every inhabited locality is retained, including one-person localities, with no population cutoff. Their published population sums to 126,014,024. National, state and municipal totals, plus aggregate locality codes 0000, 9998 and 9999, are excluded from the point roster. “City / town” and “Village / hamlet” are display groups above/below 2,500 inhabitants, not claims about legal city status. These points describe census localities rather than whole metropolitan areas.

Names, stable nine-digit source codes, DMS reference coordinates and total population are extracted from the hash-pinned national ZIP already used for municipal-seat aliases. Coordinates convert to WGS84 decimal degrees without moving the source point. The retained ten-column extract and manifest are in `scripts/boundary-sources/mexico-localities/`; the original archive remains an ignored download cache. Running `node scripts/extract-mexico-localities.mjs` reproduces the extract from the pinned archive.

Point membership links localities to the atlas’s current mapped municipalities. 851 localities fall in a different municipality from their 2020 code, including later reorganisations. Four reference points are just outside the retained land polygons (1–226 metres); those retain their official census municipality links. Every reassignment and exception is recorded in `coverage-audit.json`. Neither administrative geometry nor municipality statistics are changed.

The runtime reads a small locality manifest, geographic point chunks and a compact worker search index. The complete `settlements.bin` remains a build/validation input and is never downloaded by the map. City cards load only the selected point’s details and show its own 2020 locality population. Cancún has 888,797 residents; Benito Juárez municipality retains its separate 911,503. Breadcrumbs link each locality to its municipality and state. Saved selections retain locality identity. Municipal-seat aliases still find the administrative record, while major city results precede municipalities and tiny same-name places. Identical municipality labels give way to visible locality labels without removing either place from search.

Dot admission zooms are calculated during the data build and retain the shared 36-pixel spacing policy. Point chunks are split by zoom band and geography, contain at most 256 records each, and use a 12-chunk cache. Only visible points and the current selection are registered with the map. Small settlements appear at close zoom, coincident points remain searchable, and selected points stay visible. Municipality child lists show 100 places at a time. The map keeps two administrative levels; localities are independent points. Country overview pages remain hidden.

Use `npm run build:mexico-localities` to rebuild the point data alone. The municipal builder reapplies it when the retained source is available. Use `npm run test:mexico-localities` for complete source accounting, census scope, current parent membership, source coordinates, search and density checks, and `npm run test:mexico-localities-browser` for desktop/mobile dots, city/municipality statistics, breadcrumb navigation, tiny places, saved links, visibility controls and cleanup.

## Low-memory locality loading

The manifest under `localities/` describes 1,802 spatial chunks, their bounds and admission zooms, source defaults, parent counts and saved-link locators. It does not contain the nationwide locality roster. The map fetches only chunks intersecting the current view at the current zoom, with three concurrent requests. A 12-chunk LRU cache bounds retained tuples to at most 3,072. New camera views abort stale requests; callbacks from older views cannot replace current points. The selected locality remains available independently of camera position.

Global search starts a dedicated worker on demand. Its binary inverted index contains original UTF-8 names, numeric place and parent IDs, display classes, a sorted normalized term dictionary and posting lists. Exact-name/prefix lookup and word-prefix intersections return up to 20 lightweight results. Accents and punctuation are normalized; municipality/state terms and source codes remain searchable. Numeric columns use delta coding and byte planes before gzip. The current index is 4,905,315 compressed bytes and 18,610,018 decoded bytes. Coordinates, population figures and full place objects are absent from this index; selecting a result resolves its state locator and loads the relevant point chunk. Saved place links use those locators directly and do not start global search.

Search responses carry request IDs; the page ignores superseded queries and country generations. Enter during a pending search waits for that query’s result. Municipal locality lists request only a 100-result page when expanded. Leaving the country terminates the worker, rejects pending requests, aborts map/locator downloads, removes sources/listeners and releases cached records. Tile failures retain a Retry action. The remaining countries keep their existing settlement loaders.

Local measurements in a 390px headless Chrome viewport showed retained main-page JavaScript heap falling from approximately 238 MiB to 24 MiB. The worker’s 18 MiB index is additional and loads only when search/list browsing needs it. Warm end-to-end searches took approximately 3–14 ms, with less than 4 ms in the input handler. At 4× browser CPU throttling, warmed handlers took approximately 2–7 ms and results approximately 13–26 ms. Cold first-search and network costs are separate; the index still requires a roughly 4.9 MB download. These are local browser measurements, not physical-phone or total-process memory claims.

`npm run test:mexico-localities` additionally validates every streamed tuple, locator, compact index record, alias ranking and bounded result decoding. `npm run test:mexico-localities-browser` includes locality-budget scenarios for repeated panning, cache limits, slow-CPU input, municipal paging, stale-query cancellation, failed-tile retry and worker termination. The retained main-page heap budget after interaction is 80 MiB.
